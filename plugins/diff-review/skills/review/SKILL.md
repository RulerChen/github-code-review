---
name: review
description: Open a GitHub-style diff viewer in the browser for the uncommitted changes of a repository, or of every repository in a directory, all in one page. In the page the user can compare other branches, tags or commits and have Claude group the changes into topics. Use when the user wants to review code changes, for example "/review" or "review ~/work".
argument-hint: "[directory]"
---

Arguments: $ARGUMENTS

1. The only argument is the directory to review. A first argument that names an existing directory, absolute or relative to the current working directory, is the directory to review. Without one, review the current working directory. A directory with no `.git` of its own but repositories directly under it, such as a workspace of clones, stands for all of them in one diff. Ignore anything else in the arguments, such as a ref, a focus or topics. The user picks those in the page.
2. Call `open_diff_viewer` from the `diff-review` MCP server with `repo` set to the directory as an absolute path and `session` set to `${CLAUDE_SESSION_ID}`, and nothing else. It compares the working tree with `HEAD`. It prints the page's URL, what it compares and how many files changed, the repositories where the comparison failed, and a `curl` command that waits for the user's review.
3. Run that command with the Bash tool in the background (`run_in_background`), so you are notified when the user submits a review.
4. Your whole reply is the URL from the first line of the `open_diff_viewer` output, alone. Write no text before, between or after the tool calls of steps 2 and 3. Leave out what you are doing, what the page compares and how many files changed, how to use the page, failed repositories and restored comments, which the page shows itself, and the diff. When `open_diff_viewer` says reviews were never read, handle them as in step 5 with `get_review_comments` called without `after`.
5. When the wait command finishes:
   - If it failed, the viewer has closed. Say so and stop waiting.
   - Call `get_review_comments` with `repo` and `after` set to what the command printed. A comment's path is relative to the directory the wait command names: the repository's root, or the directory holding the repositories, where the path starts with the repository's directory. Its line numbers and quoted lines are from when it was written, so find the code by the quoted lines if it has moved. A comment on the whole file has neither and is about the file as a whole. A comment on a topic is about that topic as a whole.
   - Sort the threads by their last comment. A question asks to explain the code, asks why, whether or what happens, or is unclear, and answering it changes no file. A change request asks you to change the code, including with a ```suggestion block. Answer a question instead of guessing at a change.
   - For each question, start a fork of yourself in the background with the Agent tool, `subagent_type` set to `fork`, one per thread, all in one message. Its prompt names the thread id and says: answer only this thread and change no file; call `reply_to_review` with this one thread's reply, written as the reply rules below say; do not run the wait command or call `get_review_comments`; end with one line saying whether you replied.
   - Make the change requests yourself, one after another, then call `reply_to_review` with a reply on each of their threads.
   - Each reply is in the language of the comment. Its first sentence is the answer: what you changed, or the answer to the question, and for a comment that only asks to explain, what the lines do. When you cannot tell what a comment wants, the reply is one short question asking that. After it, add only what the user needs to follow that answer, in a short paragraph of plain sentences. Leave out who added the code and in which commit unless the comment asks, how you found the answer, a restatement of the comment, options the code did not take and limits or edge cases unless the comment asks about them, a note that you did not check something (check it, or leave the point out), and closing offers or recaps. Mention something the comment did not ask about only when it is a bug in these lines, in one last sentence. Before calling, delete a first sentence that only leads into the answer and a last sentence that offers more help or repeats what came before.
   - Tell the user in the terminal what you changed, and that Refresh in the page shows the new diff. When you changed nothing, write no text at all. Leave out the questions and the forks, whose answers show on their threads, and that you are waiting for the next review.
   - Run the wait command that `get_review_comments` printed in the background again.
6. When a fork finishes, its reply is already on its thread. Write no text at all, not even a line saying it replied. If it did not reply, answer that thread yourself.
