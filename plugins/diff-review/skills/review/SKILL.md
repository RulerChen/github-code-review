---
name: review
description: Open a GitHub-style diff viewer in the browser for uncommitted changes, the changes since a git ref, or the changes between two branches, tags or commits. When the user says how to split the changes into topics, by naming the topics or giving a rule, the changes are also grouped into those topics with an explanation of each. Works on one repository, or on a directory whose subdirectories are repositories, all in one page. Use when the user wants to review code changes, for example "/review", "review the cache changes", "review against main", "review main...feature", "review ~/work" or "review with topics cache and UI".
argument-hint: "[directory] [base-ref | base...head | base..head] [focus] [topics]"
---

Arguments: $ARGUMENTS

1. The arguments can start with the directory to review, then what to compare. The rest is the focus: what the user wants to review. All are optional.
   - A first argument that names an existing directory, absolute or relative to the current working directory, is the directory to review. Without one, review the current working directory.
   - A git ref (a branch, tag, commit or `HEAD~N`) is the `base`, compared with the working tree. Without one the base is `HEAD`.
   - `base...head` compares two refs the way a GitHub pull request does: the changes on `head` since it branched from `base`. Set `base` and `head`.
   - `base..head` compares the two refs directly. Set `base`, `head` and `threeDot: false`.
   - Refs for one repository under the directory, such as `alpha:v1.2`, `alpha:v1.2...v1.3` or "compare beta against develop", are an override: an item of `overrides` with `dir` set to the repository's directory name and `base`, `head` and `threeDot` read as above. That repository compares them, and the others compare `base` and `head`.
   - Group the changes into topics only when the user says how to split them. They can name the topics, such as "topics: cache, UI" or "split it into the parser fix and the docs", or give a rule, such as "one topic per repository". A request for topics that does not say how, such as "by topic", and a focus alone, such as "the cache changes", are no reason to group.
2. Skip this step and step 3 when the user did not say how to split the changes into topics. Otherwise call `list_changes` from the `diff-review` MCP server with `repo` set to the directory as an absolute path, plus `base`, `head`, `threeDot` and `overrides` from step 1. It covers the repository the directory is in. A directory with no `.git` of its own but repositories directly under it, such as a workspace of clones, stands for all of them in one diff: each file's path starts with its repository's directory, and each commit names its repository. It prints the commits in the range and every change with its id, and names the repositories where the comparison failed, for example because they lack the ref. If there are no changes, skip step 3 and leave out `topics` in step 4. Keep going from step 4 anyway, since the user can still pick other refs in the page or review changes made later.
3. Group the changes into the topics the user named, in their order, or into the topics their rule gives. Do not add topics of your own. Put each change in the topic it belongs to. Leave out the changes that fit none of them, and the page shows those under Other changes. Leave out a topic that no change belongs to, and tell the user. For each topic give:
   - `title`: the user's name for the topic, or a few words naming the topic their rule gives.
   - `summary`: two to six sentences of Markdown on what changed and why, naming the files and functions involved and anything the reviewer should check closely. Use the commit messages for the why. When a topic spans repositories, say how their changes fit together.
   - `ids`: the ids of all changes in the topic.
   Write titles and summaries in the language the user writes in.
4. Call `open_diff_viewer` from the `diff-review` MCP server with `repo` set to the directory as an absolute path, plus `base`, `head`, `threeDot` and `overrides` from step 1, `focus`, `session` set to `${CLAUDE_SESSION_ID}`, and `topics` from step 3 when you grouped the changes. If it reports unknown ids, fix them and call it again. It prints the page's URL, what it compares and how many files changed, the repositories where the comparison failed, and a `curl` command that waits for the user's review.
5. Run that command with the Bash tool in the background (`run_in_background`), so you are notified when the user submits a review.
6. Reply with the URL, then the topic titles as a short list when you grouped the changes. If `open_diff_viewer` says the page already open in their browser switched to the comparison, tell them to look there. If the comparison failed in some repositories, say which and why. With several repositories, tell them the repos button beside the refs at the top left of the page sets refs for each one. Tell them they can click line numbers in the page to comment on lines, or the comment button in a file's or topic's header to comment on the whole file or topic. A comment that mentions `@claude` gets an answer in the page right away. Other comments wait in their review until they press Submit review, and then you make the changes they ask for. The Topics tab can group this or any other comparison they pick into topics, and lists every review with topics opened in this session. Do not paste the diff.
7. When the wait command finishes:
   - If it failed, the viewer has closed. Say so and stop waiting.
   - Call `get_review_comments` with `repo` and `after` set to what the command printed. Address every comment: change the code where the user asks for a change, and answer questions or unclear requests instead of guessing. A comment's path is relative to the directory the wait command names: the repository's root, or the directory holding the repositories, where the path starts with the repository's directory. Its line numbers and quoted lines are from when it was written, so find the code by the quoted lines if it has moved. A comment on the whole file has neither and is about the file as a whole. A comment on a topic is about that topic as a whole.
   - Call `reply_to_review` once with a short reply on each thread, saying what you changed or answering it, in the language of the comment.
   - Tell the user in the terminal what you changed, and that Refresh in the page shows the new diff.
   - Run the wait command that `get_review_comments` printed in the background again.
