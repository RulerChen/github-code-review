---
name: review
description: Open a GitHub-style diff viewer in the browser for the uncommitted changes of a repository, or of every repository in a directory, all in one page. In the page the user can compare other branches, tags or commits and have Claude group the changes into topics. Use when the user wants to review code changes, for example "/review" or "review ~/work".
argument-hint: "[directory]"
---

Arguments: $ARGUMENTS

1. The only argument is the directory to review. A first argument that names an existing directory, absolute or relative to the current working directory, is the directory to review. Without one, review the current working directory. A directory with no `.git` of its own but repositories directly under it, such as a workspace of clones, stands for all of them in one diff. Ignore anything else in the arguments, such as a ref, a focus or topics. The user picks those in the page, as step 4 tells them.
2. Call `open_diff_viewer` from the `diff-review` MCP server with `repo` set to the directory as an absolute path and `session` set to `${CLAUDE_SESSION_ID}`, and nothing else. It compares the working tree with `HEAD`. It prints the page's URL, what it compares and how many files changed, the repositories where the comparison failed, and a `curl` command that waits for the user's review.
3. Run that command with the Bash tool in the background (`run_in_background`), so you are notified when the user submits a review.
4. Reply with the URL. If `open_diff_viewer` says the page already open in their browser switched to the comparison, tell them to look there. If the comparison failed in some repositories, say which and why. Tell them they pick other branches, tags or commits to compare with the refs at the top left of the page, and with several repositories, that the repos button beside the refs sets refs for each one. Tell them they can click line numbers in the page to comment on lines, or the comment button in a file's or topic's header to comment on the whole file or topic. Comments wait in their review until they press Submit review, which sends them to you, and you answer their questions and make the changes they ask for; Send now on a comment sends just that one to you at once. In the Topics tab they can have you create topics for the comparison they pick, with a focus, or edit the topics, renaming, adding, removing or reordering them, and have you redo them; its Reviews list brings back the earlier topics of this session. If `open_diff_viewer` says it brought back comment threads, tell them the comments from before are in the page again, and when it says reviews were never read, handle them as in step 5 with `get_review_comments` called without `after`. Do not paste the diff.
5. When the wait command finishes:
   - If it failed, the viewer has closed. Say so and stop waiting.
   - Call `get_review_comments` with `repo` and `after` set to what the command printed. Address every comment: change the code where the user asks for a change, and answer questions or unclear requests instead of guessing. A comment's path is relative to the directory the wait command names: the repository's root, or the directory holding the repositories, where the path starts with the repository's directory. Its line numbers and quoted lines are from when it was written, so find the code by the quoted lines if it has moved. A comment on the whole file has neither and is about the file as a whole. A comment on a topic is about that topic as a whole.
   - Call `reply_to_review` once with a reply on each thread: a short paragraph of plain sentences that says what you changed or answers it, in the language of the comment.
   - Tell the user in the terminal what you changed, and that Refresh in the page shows the new diff.
   - Run the wait command that `get_review_comments` printed in the background again.
